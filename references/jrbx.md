# 睿销（jrbx）聚合站适配器

聚合全国招标采购网站的商业数据库，运营方深圳市华宇医疗科技有限公司。
适配器脚本 `scripts/jrbx_search.py`，统一入口 `scripts/tender_search.py`。

## 与其他来源的本质差别

CCGP 和 PLAP 是官方一手站点，匿名可访问；睿销是**需要账号登录的商业聚合库**。
它是本技能唯一携带用户登录态的来源，因此单列本节的凭证与配额约束。

## 凭证

微信扫码登录 `https://www.jrbx.com` 后，登录态由 localforage 存在 **IndexedDB**
（库 `localforage`／对象仓库 `keyvaluepairs`／键 `USER_INFO#1`），不是 localStorage。
浏览器控制台取值：

    indexedDB.open('localforage').onsuccess=e=>{const r=e.target.result.transaction('keyvaluepairs').objectStore('keyvaluepairs').get('USER_INFO#1');r.onsuccess=()=>console.log(JSON.stringify(r.result))}

适配器只读三个字段，从环境变量或 `config/jrbx.json` 注入，**不得写入仓库、载荷或日志**
（落盘和报告里的 `user_id` 一律只留前四位）：

| 环境变量 | 来源字段 |
|---|---|
| `JRBX_USER_ID` | `userId` |
| `JRBX_TOKEN` | `accessToken`（注意请求体里的键名是 `token`） |
| `JRBX_OPENID` | `openid` |

`accessToken` 是 JWT，实测有效期 **20 天固定窗口**（`iat`→`exp`），每天调用不会顺延。

### 写入与读取顺序

```
python scripts/jrbx_search.py --set-token
```

粘贴上面控制台语句打印出的整段 JSON，Ctrl+Z 回车（Windows）／Ctrl+D（macOS/Linux）结束。
脚本自己从任意嵌套层级里挖出 `userId`／`accessToken`／`openid`，写进 `config/jrbx.json`
（权限收到 `0600`），并直接打印到期日、剩余天数与写入后的账号池规模。

`config/jrbx.json` 存的是**账号池**，形如 `{"accounts": [{userId, token, openid}, ...]}`。
换个微信号再扫一次、再跑一遍 `--set-token` 就是加一个账号：**同 `userId` 就地覆盖**
（重新扫码换发，不打乱轮换顺序），**新 `userId` 追加到池尾**。旧的三字段平铺格式仍然读得动，
等价于只有一个账号的池。撞废的账号手动从 `accounts` 里删掉即可，脚本不自动改这个文件。

读取顺序：**三个环境变量全齐时优先用环境变量；否则回退 `config/jrbx.json`。**
两者都没有才报错。注意环境变量**只表达得了一个账号**——要用多账号就走配置文件。
命令行**始终不接受**凭证明文——避免进入进程列表和 shell 历史。

`config/jrbx.json` 与 `config/webhook.json` 同等对待：在 `.gitignore` 中，
**只允许留在本机**，禁止提交、外发，也不得进候选目录、日志或 Webhook 载荷。
模板见 `config/jrbx.example.json`。

定时任务两种装法都行——服务账号跑就设用户级环境变量，本机跑就用配置文件，
不必两边都配。

## token 维护

睿销**没有 refresh／续期接口**。前端只有三个登录相关接口：`/cs/wx/v1/loginQrCode`
取二维码、`/cs/wx/v1/scanLoginResult` 轮询扫码结果、`/v1/outside/login`（CRM 的
`partnerLogin`，属企业版员工体系，本技能用不上）。**唯一换发路径是微信重新扫码**，
按日常定时任务计约每年 18 次。

返回码 `08`（重复登录）在前端与"登录过期"走同一处理分支——清本地登录态并强制重登，
说明该站是单会话的。**为其他用途重新扫码可能顶掉定时任务在用的 token**，换发后要同步
更新环境变量。（该结论由前端错误处理路径推断，未实测。）

### 预检命令

```
python scripts/jrbx_search.py --check-token
```

**逐个**预检池里的每个账号，输出 JSON 报告：外层是池级结论
（`account_count`／`usable_account_count`／`status`／`message`），`accounts` 数组里是逐账号明细。
`user_id` 一律只留前四位——三字段都是登录态，不进日志也不进报告。

退出码取**池里最健康的那个账号**的状态，因为只要还有一个能用，检索就不该停：

| 退出码 | status | 含义 | 处置 |
|---|---|---|---|
| 0 | `ok` / `unknown_expiry` | 至少一个账号正常 | 无需动作 |
| 4 | `expiring_soon` | 能用的都快到期了（低于 `--warn-days`，默认 3） | 安排重新扫码 |
| 3 | `expired` / `rejected` / `rate_limited` | 没有一个能用：过期、被顶号，或被判频控 | 必须重新扫码 |
| 2 | `probe_failed` | 网络或接口异常，**不代表凭证失效** | 重试即可 |

即使退出码是 0，`message` 里也会点名那些已经不能用的账号——池在缩水这件事不能被
「今天还跑得动」盖过去。

只解析 JWT 的 `exp` 发现不了「被顶号」和「被判频控」——那两种情况下 token 还没到期但
服务端已拒绝。因此预检默认对每个账号额外发一次最小检索（`pageSize=1`）验证服务端是否
仍接受该凭证；这次请求**不消耗回源配额**。`--offline` 可跳过该探测，只做离线有效期解析
（离线模式查不出频控，`rate_limited` 只有联网探测才判得出来）。

适合放在定时任务的检索步骤之前，把「快到期」和「已失效」在真正跑检索前就暴露出来。

## 多账号轮换

**`1403`「操作过于频繁」实测是一次性的：撞上之后该账号即废，退避重试无济于事。**
因此适配器不重试，而是把当前账号退池、换池里的下一个**原地重发同一请求**——
请求序列既不丢也不重跑，等价于在被打断的那一步续上，整趟检索照常跑完。
`05`／`06`／`08`／`40` 这类登录态故障同样先换号再重发，只有池里**一个账号都不剩**
才中止：频控用退出码 5（`JrbxRateLimitError`），登录态失效仍是 3。

改造前的行为是反过来的，值得记一笔：撞上 1403 后退避重试 2 次，耗尽后只 `break` 掉当前
query 的分页循环、**接着打下一条 query**。按 85 条清单算，第 20 条撞上就意味着后面还要
再发约 195 次请求全砸进同一个频控窗口——服务端给的第一次警告被放大成了几百次违规。

约束：

- 池是**串行**用的，同一时刻只有一个账号在发请求，不并发、不做负载分摊。
  多账号只解决「撞上之后能不能把这一趟跑完」，不用来提高吞吐。
- 换号后出口 IP 没变，而站点刚说过太快，因此换号时先空出一个长停顿再续。
- 退池只在**本次进程内**生效，不回写 `config/jrbx.json`。撞废的账号下次仍会被试一次
  （代价是一次请求），要清理就手动从 `accounts` 里删掉，用 `--check-token` 认人。
- 摘要里的 `account_count` 与 `accounts_retired` 记录本次用了几个账号、谁退了池、
  退池前发了多少次请求；`user_id` 只留前四位。退池时同时往 stderr 打警告——
  池在缩水不是「今天没情报」，无人值守时必须喊出来。

### 节流

固定间隔是很明确的机器指纹，而 1403 一撞账号就废，宁可跑慢也别撞：

| 参数 | 默认 | 作用 |
|---|---|---|
| `--delay` | 1.2 | 请求间隔**下限**秒数 |
| `--delay-jitter` | 1.8 | 叠加在下限之上的随机抖动上限，实际间隔 1.2~3.0s；0 表示等距发包 |
| `--pause-every` | 25 | 每发这么多次请求插一次长停顿，0 表示关闭 |
| `--pause-seconds` | 20 | 长停顿基准秒数，实际按 ±50% 随机 |

按 85 条清单一趟约 200 次请求估算：平均间隔 2.1s，外加 8 次长停顿，整趟约 10 分钟。
`--delay 0` 会**同时**关掉抖动与长停顿，那是 `--check-token` 单次探测用的路径，
不要拿它跑检索。

## 接口

网关是 `https://www.jrbx360.cn`（`www.jrbx.com` 只是前端）。全部为 POST JSON，
凭证三字段平铺在请求体里，不走 Header。

| 路径 | 用途 | 关键入参 |
|---|---|---|
| `/integrated-search/v1/search` | 列表检索 | `keywords`、`timeType`、`startTime`、`endTime`、`noticeTypes`、`pageNum`、`pageSize` |
| `/integrated-search/v1/verify/noticeDetail` | 公告正文 | `noticeId`（**只传这一个**；额外传 `year` 会返回 04） |
| `/integrated-search/v1/verify/getNoticeOriginalUrl` | 回源原始公告 URL | `noticeId` |

响应外层为 `{code, message, content}`。前端会把 `content` 改名成 `data`，抓包对照时注意。

### keywords 是 AND 语义

`keywords` 是数组，多个词之间取交集（实测 `['过敏原']`=9292、`['试剂']`=1260971、
两者同传=5220）。清单里的 `+` 表示 AND，例如 `过敏原+试剂` 会传 `["过敏原","试剂"]`。

**只有 AND，没有 OR**（2026-09-03 实测，对照表见 keywords.md）：单串里的空格和竖线都只是
分词符，分完仍取交集；`OR` 被当成第三个词一起 AND，`+` 根本不是分隔符、整串当一个词搜。
匹配是**精确子串**，不是分词后的词项匹配——`IgG亚类` 命中 0 而 `亚类` 命中 7。

列表响应的计数字段是 `totalCount`（`totalPage` 会随 `pageSize` 变），没有 `total` 字段。

### 时间窗

`timeType` 传 `custom`，配 `startTime`／`endTime` 的**毫秒**时间戳，过滤作用于 `publishTime`，
结果按发布时间倒序。也接受 `全部`／`今天`／`最近七天` 等中文标签，适配器不使用。

### 公告类型码

`noticeTypes` 传字符串码数组。完整枚举（72h 采样实测）：

| 码 | 名称 | 是否可行动 |
|---|---|---|
| 20100 | 招标 | ✅ 默认启用 |
| 20300 | 预告 | ✅ 默认启用（采购意向，提前量最大） |
| 20400 | 变更 | ✅ 默认启用（在售标的改截止时间或参数） |
| 20600 | 资格预审 | ✅ 默认启用 |
| 20200 | 结果 | ❌ 已有结论 |
| 20201 | 中标 | ❌ 已有结论 |
| 20203 | 废标 | ❌ 已有结论 |
| 20205 | 终止 | ❌ 已有结论 |
| 20206 | 入围 | ❌ 已有结论 |
| 20500 | 合同验收 | ❌ 已有结论 |
| 20501 | 合同 | ❌ 已有结论 |
| 20502 | 验收 | ❌ 已有结论 |
| 20700 | 其他 | ❌ 噪声占比高 |

服务端过滤掉「已有结论」这一类，等价于管线 `prepare` 阶段的 `concluded` 排除，
但省掉了把它们取回本地再丢弃的开销。

## source_url 的两级策略

睿销有两种可用链接，适配器按优先级取：

1. **回源原始站点链接**（`getNoticeOriginalUrl`）——匿名可访问，且能与 CCGP/PLAP
   在规范 URL 层直接命中同一身份键，跨来源去重效果最好。`source_priority` 300。
2. **睿销主站正文永久链接**——回源配额耗尽时兜底。`source_priority` 250，
   合并时让位于回源版本。

主站永久链接格式（前端 811 模块 `pp` 函数，`window.open` 到 `NODE_SERVER_IP`）：

    https://www.jrbx.com/article/detail?id=<noticeId>&year=<year>

`id` 与 `year` **两个参数缺一不可**，都来自列表项。该路由用直连 curl 校验会看到
Next.js 的 404 骨架，那是全客户端渲染应用的 SSR 兜底，**不代表路由不存在**——
判据是页面加载了 `static/chunks/app/article/detail/page-*.js`，而不存在的路由只会
加载根 layout 与 error chunk。

**该链接需登录睿销账号才能打开**，因此这类候选标记 `site_name: 睿销`、
`auth_info_des: 商业聚合库正文永久链接，需登录睿销账号打开`。适配器已保存完整正文
（`retrieval_verified: true`、`content_access: public_full`），模型核实时不必打开该链接，
但推送给销售的`链接`字段需要对方有睿销账号。

只有 `id` 或 `year` 缺失、两种链接都拼不出时才丢弃候选，计入 `dropped_no_url`。
**任何情况下都不得伪造链接占位。**
（实现注意：`canonical_url("")` 会返回 `"/"`，判空必须在调用它之前做。）

## 回源 URL 的每日配额

`getNoticeOriginalUrl` 对免费账号（`vipStatus: 0`）是**每日配额制，实测约 10 次/天**：

- 配额耗尽后一律返回 `07 抱歉,您没有使用权限`；
- 判据是「同一条 20 分钟前成功、之后返回 07」，且详情里 `canShowOriginalUrl` 仍为 `true`
  ——该字段只表示「这条有原始链接」，不表示「你有权限看」；
- 列表检索与公告正文**不受该配额影响**，实测配额耗尽后仍正常返回 `00`。

因此适配器的策略是：列表与正文放开取，**回源调用只花在通过目标品类预筛的候选上**，
按发布时间倒序，上限由 `--max-origin-lookups` 控制（默认 10）。一旦收到 `07`
立即停止后续回源尝试，不再空烧请求；其余候选改用主站正文永久链接，
计入摘要的 `fallback_article_url_count`。

把 `--max-origin-lookups` 设为 0 可以完全跳过回源、全部走主站链接，
适合把配额留给人工在网页端使用的场景。

## 返回码

| code | 含义 | 适配器处理 |
|---|---|---|
| `00` | 成功 | 正常 |
| `02` | 缺必要参数 | 视为脚本缺陷，直接失败 |
| `04` | 找不到公告 | 跳过该条 |
| `05` | 无效 token | 换号原地重发；池空则**中止并报警**，需重新扫码 |
| `06` | 登录过期 | 换号原地重发；池空则**中止并报警**，需重新扫码 |
| `07` | 无使用权限 | 回源配额耗尽；停止回源，保留其余结果 |
| `08` | 重复登录（被顶号） | 换号原地重发；池空则**中止并报警**，需重新扫码 |
| `11` | 关键词兑换受限 | 记入失败但继续 |
| `40` | 未关注公众号 | 换号原地重发；池空则**中止并报警** |
| `1403` | 操作过于频繁 | **该账号即废**；不重试，换号原地重发，池空则中止（退出码 5） |

`05`／`06`／`08`／`40`／`1403` 都先尝试换号续跑；池里一个账号都不剩时必须单独报警，
**不得当成空结果吞掉**——无人值守定时任务会因此静默失效。
`tender_search.py` 把退出码 3 与 5 一并计入 `source_auth_failed`。

## Query 清单

清单在 [keywords.md](keywords.md)「检索 Query 清单」，与 CCGP 共用，两者都是全文检索。
本适配器不另存副本。

`keywords` 数组是 AND（交集），清单里的 `+` 表示组词，例如 `过敏原+试剂` 会传
`["过敏原","试剂"]`。现行清单是一行一条的单词，没有用到组词——**2026-09-03 实测确认睿销
不支持 OR**，合并不了 query（对照表见 keywords.md「能不能合并成更少的 query」）。
同批测出引擎是**精确子串匹配**，取词按「每行取最短写法」，实测数记在 keywords.md。
复测：`python scripts/jrbx_search.py --probe-keyword-syntax`。
