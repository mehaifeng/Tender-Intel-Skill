## 0. 使用总则（阶段 1 检索）

- 每日按「§5 每日 Query 清单」执行 **49 条**查询：A/B 层 23 条 + C 层长尾词 15 条 + D 层意图词分层覆盖块 11 条。**每天完全相同——不轮换、不随机、不按星期挑组。**
- 检索由 `scripts/doubao_search.py` 直连豆包搜索 Custom 版官方 API 执行（2026-08-18 起，替代第三方 MCP）。**本清单即脚本的配置源**——脚本从 §5 解析 query，不另存一份，改这里就是改运行行为。
- 官方参数固定：`TimeRange=45d`（展开为闭区间）、`Count=20`（官方上限 50）、`AuthInfoLevel=0`（官方请求侧只有 0/1，0=不限制）、`NeedUrl=true`、`ContentFormats=markdown`（详见 SKILL.md 阶段 1）。
- **每条候选记录来源 query 编号**（`found_by_query`），由脚本在跨 query 去重时生成，用于 §12 的边际贡献裁撤。该字段只进 seen.json，**绝不进飞书载荷**。
- **执行前校验由脚本强制**：编号连续、条数与本节声明一致、每条末尾带意图词、长度 ≤100 字符（API 上限，超长会静默截断掉末尾的意图词）。任一不过直接中止，不发请求。
- 候选收集后**先按 `source_url` 跨查询去重**，再进入阶段 2——同一页面会被多条 query 同时命中，不去重则核实成本翻倍。
- 一手、第三方和聚合网站的可访问详情页都可作为候选；第三方/聚合网站的结果 URL 即为 `source_url`。
- **为什么不轮换**（2026-08-14 定）：轮换省调用量，代价是发现延迟——某个词组最长要等 6 天才轮到，而采购意向的全部价值就在提前量（提前 30 日发布，是唯一还能影响技术参数的窗口），6 天延迟是实打实的损失。固定全量还有第二个好处：**每天清单相同，命中数的变化只能归因于"有没有新公告"**，可以直接做日对比；轮换会让日间差异混入"今天换了组词"这个噪声，看不出趋势。代价是调用量由 24 升至 46（2026-08-18 再增至 49）。
- **为什么 `Count` 从 10 提到 20**（2026-08-18 定）：真实的漏采模式不是"意图不对所以没检索到"，而是"文档在结果集里但排在第 11 位"。49×10 = 490 个槽位是硬天花板——**同样 49 次调用，结果深度翻倍**，直接打在这个失败模式上，比新增 query 划算。代价要认：候选量上升，**核实端**（curl→SPA 反查→MinerU→浏览器）的负载随之上升，而核实才是本管线真正的成本大头。实测 2026-08-18 全量运行：49 条 query → 771 条原始结果 → 去重后 **638 条候选**。若某日候选量超出可核实范围，优先按 §12 裁撤零贡献 query，而不是把 Count 调回 10。
- **官方上限是 50，20 不是天花板**：旧的第三方 MCP 把 `count` 卡在 20，直连官方 API 后还有 2.5 倍深度余量（`--count 50`）。留着不用是有意的——当前瓶颈已经在核实端，不在检索深度。哪天判断深度确实不够，这条路是通的。**但注意 `count` 只是上限不是保证**：2026-08-18 实验里给 `count=50` 的合并 query 实际只返回 6~17 条，召回由 query 本身决定，调大 count 不会凭空变出结果。
- **为什么是 49 条而不能更少**（2026-08-18 实测）：首日归因显示 **85% 的候选只有一条 query 能捞到**（544/638，被 2 条以上同时命中的仅 94 条）——清单不冗余，砍一条就是少一批候选。同日的合并实验（§4）进一步证明"合并条数省调用"不可行。可精简的空间只有 §12 观察名单里那三条高冗余 query，占 6%。
- **屏蔽域名**：`BlockHosts` 固定屏蔽 `yaozh.com`（药智网注册证库）、`bio-equip.com`、`biomart.cn`（生物器材/生物在线产品页）、`toutiao.com`（新闻科普）、`thermofisher.cn`（厂商产品目录）。2026-08-18 实测这 5 个域名贡献了 638 条候选中的 **185 条（29%），全部不是招标公告**，且 §6 排除词表拦不住它们（那张表拦的是"服务/食堂/体检"）。API 上限就是 5 个，已用满。屏蔽在检索侧发生，直接省掉整个核实成本。
- **每月调用量**：49 条 × 30 天 = 1470 次。火山账号每月免费额度 500 次，本管线一直在付费区间运行；账号维度默认 5 QPS，脚本按 4 QPS 限流，全量跑一轮约 30 秒。
- 本词表所有词**双重用途**：①组拼检索（§5）；②核实阶段品类匹配（§11 判定细则、阶段 4 `matched_category` 判定）。

### 3.2 D 层：意图词分层覆盖块

固定清单（§5 第 1~38 条）只用了 `招标公告` / `采购公告` / `招标` / `采购` 四个主变体。四个扩展变体由本块覆盖——但**不是均摊占位**：意图词按**检索独立性**分三层，只对独立性高的单独扩位。

**分层依据（2026-08-18 定，据 seen.json 前 44 条实测）**：44 条记录出现了 **20 种 notice_type**，而当时 46 条 query 只用了 8 个意图词。逐条比对后，**17 条记录（39%）的公告类型从未作为意图词出现在任何 query 里**——单一来源公示 3、更正公告 2、中标公告 2、合同公告 2，以及征求供应商信息 / 遴选公告 / 需求参数公示 / 流标公告 / 比选公告 / 议价公告 / 采购需求公告 / 单一来源公告 各 1。procurement_method 一列同样：比价采购、方案征集、院内议价、市场调研询价、快速采购，全部来自从未检索过的词。

原因是**意图词匹配的是正文，不是标题**：一份《比选公告》的正文里必然写满"采购人""采购项目""采购预算"，裸 `采购` 的 query 早就把它捞回来了。

所以：**意图词是领域开关（有 vs 无，差别巨大——见 §4 的 8-14 对照实验），不是文种闸门（换一个词，差别很小）**。据此**不做**"品类词 × 全部意图词"的笛卡尔积（#1~38 × 8 = 304 条/天，6.6 倍调用量）——它买回来的绝大部分是同一批 URL 的重新排序，跨 query 去重会直接吃掉。**否决理由是边际召回低，不是贵**：本管线的成本大头在核实端、随去重后唯一 URL 数增长，检索调用本身很便宜；用成本做检索决策会把判断带偏。

| 层 | 意图词 | 与主变体的正文重合度 | 占位策略 |
|---|---|---|---|
| A | 招标公告 / 采购公告 / 招标 / 采购 | —（本身即主变体） | 每条 query 末尾带一个，跨组分散（§5 第 1~38 条） |
| B | 询价公告 / 磋商公告 / 谈判公告 | **高**——三者都是**采购方式**而非公告品类，正文必含"采购"，A 层已覆盖 | 各 2 条泛化位兜排序（§5 第 39~44 条），**不下沉到关键词级** |
| C | 采购意向 | **低**——**独立文种**：标题模板不同、正文常通篇无"招标"（只写"拟于X月采购"）、发布频道独立（省级采购意向公开专栏） | **5 条**，按品类线铺开（§5 第 45~49 条） |

**为什么只有采购意向值得扩位**：它同时满足两个条件——①检索独立性高，A 层的 `采购`/`招标` 捞不到；②业务价值最高（不晚于采购活动开始前 30 日发布，是唯一还能影响技术参数的窗口）。B 层三个词只差在排序，扩位买到的是重复 URL；给它们各留 2 条泛化位，是兜"存在但排不进 top-N"的情况，够了。

- **试剂线**：过敏原 自身抗体 免疫诊断试剂
- **仪器线**：化学发光 酶免 免疫分析仪

|---|---|---|
| 询价公告 | §5 第 39 条 | §5 第 40 条 |
| 磋商公告 | §5 第 41 条 | §5 第 42 条 |

**待验证假设（多意图词堆叠）**：§4 规定"同一条 query 只用一个意图词，不堆砌"，但 8-14 实验只比过"零意图 vs 一意图"，**从未比过"一意图 vs 多意图"**。原设想是豆包作为语义检索可能把 `过敏原 sIgE 检测试剂 招标 采购 询价 采购意向` 当软 OR 处理，若成立则以 1× 成本拿到并集覆盖。

## 4. Query 组拼规则

**意图词是领域开关，品类词是内容开关，两者缺一不可**。实证（2026-08-14 对照检索）：`过敏原特异性IgE 总IgE 检测试剂` 无意图词 → 召回医院科室科普文；加 `采购公告` → 召回中国政府采购网招标公告。没有意图词的 query，招标页排不进 top-N，等于漏采。

- **结构**：`[3~6 个语义相关品类词] + [意图词] + [可选年份 2026]`
- **意图词必带，无例外**——这是解决"不准"的**主要**闸门，第二道是核实阶段的排除词表 §6。

  > 2026-08-18 更正：旧版这里写的是"第二道闸门 `auth_level=2`"，不成立。官方请求侧 `AuthInfoLevel` 只有 0（不限制）/ 1（仅非常权威）两个取值，1~4 分级是**响应字段**的取值，被旧的第三方 MCP 当成请求参数错误地暴露了出来。本管线取 `AuthInfoLevel=0`（一手源与第三方聚合站都要收），**这一道过滤实际上不存在**——精度全靠意图词和 §6 排除词表撑着。
- **意图词库**（拼在品类词之后，每条选一个）：
  - 主变体：`招标公告` / `采购公告` / `招标` / `采购`
  - 扩展变体：`询价公告` / `磋商公告` / `谈判公告` / `采购意向`——由 §3.2 的 D 层分层覆盖块承担，**按检索独立性分配位数**：询价/磋商/谈判各 2 条泛化位，采购意向 5 条按品类线铺开。都不是备而不用的备选项。
  - **不必穷举文种词**：比选 / 议价 / 遴选 / 流标 / 征求供应商信息 / 需求参数公示等文种，其正文必含"采购"，A 层的裸 `采购` 已实测捞得到（§3.2 分层依据）；**不要为新看到的文种名新增 query**，先按 §12 看它是不是已被现有 query 覆盖。
  - **变体分散使用**：不同站群用词习惯不同（政采网多"采购公告"、公共资源交易中心多"招标公告"、医院官网多"采购"），全清单统一成一个词会漏站群；但同一条 query 只用一个意图词，不堆砌（该规则的待验证情况见 §3.2 末）。
- **执行前校验**：逐条核对当天清单每条 query 末尾是否含意图词；缺失的补 `采购公告` 再执行。
- **同组拼、跨组不拼**：同谱系词可共存一条 query；跨谱系（狼疮谱 + 自免肝谱）不混拼，避免信号稀释。**唯一例外是 D 层分层覆盖块**（§5 第 39~49 条）：这 11 条允许跨谱系/跨线拼词，因为询价/磋商/意向类公告多为单位级多品类清单，泛化词不会稀释信号，反而提高单条命中的品类覆盖。其中第 46、47 条跨自免谱系（自免肝 + 肌炎 + 类风湿 + 甲状腺）即依据本例外。
- **一条 query 品类词不超过 6 个**：超过时优先保留更具体的词，泛化词交给 A 层查询兜底。

  > **2026-08-18 实验证实（此前只是理论）**：取 4 对同谱系 query，原版各 `count=20` 分开跑，合并版 `count=50` 单跑（槽位 50 > 40，对合并有利），比对 URL 集合——合并版只保住 A∪B 的 **28%**（93 条里 26 条），且**返回条数远填不满 count**（只回 6~17 条）。最干净的对照是 C4 细胞因子组：两条原 query 本就同用 `采购` 意图词，无意图词变量干扰，品类词由 6 个并成 10 个后**召回率 10%**。食物过敏原组更极端：合并后返回的 11 条与原来 32 条**零重合**，整个跑到另一个文档集。
  >
  > 结论：**词数与召回强负相关，6 个是硬上限，不是保守估计**。"用 query 长度余量合并条数以省调用"这条路已验证不通——49 条的规模不是冗余，是必需。同一实验里跨小组合并（仪器线）拿到 49%、新增 0 条，说明"跨组不拼"这条规则**证据不足但未被推翻**，真正起作用的是词数而非跨组。
- **变体补查**：错写变体（过敏源）与同义变体（变应原/变态反应）平时并入主词 query；某条 query 连续数日零新命中时，用变体词单查一次补漏。这属**计划外的人工补查**，不计入每日 49 条，也不改变清单本身。
- **年份**：可加"2026"提精度；时效主要由 `TimeRange=45d` 承担，年份不强制。

## 11. 判定细则

**品类匹配**：公告清单中出现上述细分类对应的具体品名（如"过敏原特异性IgE抗体检测试剂盒"→过敏原sIgE试剂；"全自动化学发光免疫分析仪"→化学发光免疫分析仪）即算命中。只写"试剂一批""生物试剂盒"等笼统表述的，`match_level: "unknown"`，不得臆断匹配。对照词用 §1~§3 全部分层词表。

**参与可行性**：

- 文件获取/报名截止已过但投标截止未过 → 参与窗口实际关闭，需在 notes 里注明（除非招标文件可直链下载，此时建议电话确认参与资格）
- 单一来源公示 → 不是投标机会，作情报（记 designated_supplier）
- 中标公告/供货合同公告 → 已成交，作情报（记 winner / award_amount，竞品与自家品牌中标均收）
- 投标截止已过的招标/采购公告 → **不剔除**，转研究流作情报（status: intel，notes 注明已截止；winner 填 "null"）
- 采购意向/招标意向等探索性公告 → 未正式招标、无投标窗口，转研究流作情报（status: intel）

**品牌与排除词**：核实前先用 §6 排除词表快速预筛（服务、食堂、体检、外送、配送类大概率无效，确认后剔除）；"单一来源"不按排除处理，转情报。公告清单中出现 §7 品牌词表内品牌时，按品牌词表规则在 notes 标注。

**旧记录识别**：备案编号年份早于当前年份较多（如 2019）且页面无发布日期/截止时间的，按旧记录剔除。

## 12. 清单演进规则（query 归因与裁撤）

清单是固定的，但**不是永久的**——它按数据演进，不按直觉演进。2026-08-18 前无法评估任何一条 query 的价值：seen.json 每条记录存了 30 个字段，唯独没有"这条是哪个 query 捞到的"，于是"要不要加词、要不要扩意图"只能靠猜。本节把它变成算术题。

**归因数据（阶段 1、5 采集，见 SKILL.md）**：

- 每条候选记 `found_by_query`（命中它的 query 编号数组，如 `[3, 27]`）——同一 URL 被多条 query 命中时全部记上，这正是判断"哪条 query 可被替代"的依据
- 每日按 query 写一行统计到 `data/query_stats.json`：
  - `raw`：该 query 返回的候选数
  - `unique`：去重后**仅由该条 query 命中**的 URL 数（其余 48 条都没捞到）——**这是唯一有意义的贡献指标**，`raw` 高但 `unique` 恒为 0 的 query 是纯冗余
  - `pushed`：其中最终核实通过并推送成功的条数

**裁撤规则**：

1. 连续 **14 个运行日** `unique` 恒为 0 的 query → 裁撤，并在本文件变更说明里记一行（词表本身不删，词继续用于阶段 3 品类匹配）
2. 连续 14 日 `unique` > 0 但 `pushed` 恒为 0 的 query → 它在捞独有的东西，但捞的不是业务要的；先查 §6 排除词与 §10 细分类枚举是否需要补，再决定裁撤
3. **裁撤腾出的名额优先给 §3.2 的 C 层（采购意向）继续铺品类线**，保持每日总量不变；总量上调需要像 8-14、8-18 一样在变更说明里写明理由
4. 样本不足 14 日不得裁撤——单日零贡献只能说明当天没有这类公告

**已在观察名单**：

1. **§5 第 39 / 41 / 43 条**（D 层 B 类：同一套 keywords「过敏原 自身抗体 免疫诊断试剂」分别配 询价公告 / 磋商公告 / 谈判公告）。2026-08-18 首日归因：三条各 raw≈20 而 `unique` 均为 **2**，**冗余率 90%**。同日对照，第 45~49 条（同一个意图词「采购意向」配不同 keywords）`unique` 为 12/13/11/13/16，均值 13.0。

   两组构成一个天然对照：**换 keywords 的边际召回是换意图词的 6.5 倍**。这与 §3.2 的分层依据一致——意图词是领域开关不是文种闸门，同 keywords 换意图词买到的主要是同一批 URL 的重新排序。仅 1 个运行日，按本节规则**不得裁撤**；满 14 日若维持此形态，这三条是第一批裁撤对象，腾出的位继续给采购意向铺品类线。

2. **§5 第 31~34 条**（C4 细胞因子，18 个词占 4 条位、日预算 8.2%）在 seen.json 前 44 条记录里 `matched_category` 命中为 0，且 §10 细分类枚举中没有细胞因子对应类目。注意首日归因其 `unique` 为 17/15/14/14，检索侧贡献并不低——问题在**捞回来的东西无处归类**，属本节裁撤规则第 2 条（unique>0 但 pushed 恒为 0）的典型形态。若确认保留，需先在 §10 补一个能承接它的细分类。
