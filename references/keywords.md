## 0. 使用总则（阶段 1 检索）

- 每日按「§5 每日 Query 清单」执行 **30 条单词查询**。**每天完全相同——不轮换、不随机、不按星期挑组。**

### 3.2 D 层：意图词分层覆盖块（2026-08-26 作废）

> **本节已作废，仅作历史记录保留。** 前提是「Query 可以拼接意图词」，而官方文档明写 `Query` 不支持多词搜索，实测加空格即归零（§4）。意图约束现由 `Sites` 白名单承担：结果被限定在招标聚合站域名内，天然只有招采内容，不需要 Query 层再表达意图。
>
> 本节结论中**仍然成立**的部分：「意图词是领域开关，不是文种闸门」——正文里必含"采购人""采购项目"，所以不必为 `比选`/`议价`/`遴选`/`流标` 等文种名单独建词。这条在白名单方案下依然适用，且更彻底：白名单已保证全是招采页面。

固定清单（§5 第 1~38 条）只用了 `招标公告` / `采购公告` / `招标` / `采购` 四个主变体。四个扩展变体由本块覆盖——但**不是均摊占位**：意图词按**检索独立性**分三层，只对独立性高的单独扩位。

**分层依据（2026-08-18 定，据 seen.json 前 44 条实测）**：44 条记录出现了 **20 种 notice_type**，而当时 46 条 query 只用了 8 个意图词。逐条比对后，**17 条记录（39%）的公告类型从未作为意图词出现在任何 query 里**——单一来源公示 3、更正公告 2、中标公告 2、合同公告 2，以及征求供应商信息 / 遴选公告 / 需求参数公示 / 流标公告 / 比选公告 / 议价公告 / 采购需求公告 / 单一来源公告 各 1。procurement_method 一列同样：比价采购、方案征集、院内议价、市场调研询价、快速采购，全部来自从未检索过的词。

原因是**意图词匹配的是正文，不是标题**：一份《比选公告》的正文里必然写满"采购人""采购项目""采购预算"，裸 `采购` 的 query 早就把它捞回来了。

所以：**意图词是领域开关（有 vs 无，差别巨大——见 §4 的 8-14 对照实验），不是文种闸门（换一个词，差别很小）**。据此**不做**"品类词 × 全部意图词"的笛卡尔积（#1~38 × 8 = 304 条/天，6.6 倍调用量）——它买回来的绝大部分是同一批 URL 的重新排序，跨 query 去重会直接吃掉。**否决理由是边际召回低，不是贵**：本管线的成本大头在核实端、随去重后唯一 URL 数增长，检索调用本身很便宜；用成本做检索决策会把判断带偏。

| 层 | 意图词 | 与主变体的正文重合度 | 占位策略 |
|---|---|---|---|
| A | 招标公告 / 采购公告 / 招标 / 采购 | —（本身即主变体） | 每条 query 末尾带一个，跨组分散（§5 第 1~38 条） |
| B | 询价公告 / 磋商公告 / 谈判公告 | **高**——三者都是**采购方式**而非公告品类，正文必含"采购"，A 层已覆盖 | 各 2 条泛化位兜排序（§5 第 39~44 条），**不下沉到关键词级** |
| C | 采购意向 | **低**——**独立文种**：标题模板不同、正文常通篇无"招标"（只写"拟于X月采购"）、发布频道独立（省级采购意向公开专栏） | **5 条**，按品类线铺开（§5 第 45~49 条） |

**为什么只有采购意向值得扩位**：它同时满足两个条件——①检索独立性高，A 层的 `采购`/`招标` 捞不到；②业务价值最高（不晚于采购活动开始前 30 日发布，是唯一还能影响技术参数的窗口）。B 层三个词只差在排序，扩位买到的是重复 URL；给它们各留 2 条泛化位，是兜"存在但排不进 top-N"的情况，够了。

B 层泛化位用的两条品类线：

- **试剂线**：过敏原 自身抗体 免疫诊断试剂
- **仪器线**：化学发光 酶免 免疫分析仪

| 意图词 | 试剂线 | 仪器线 |
|---|---|---|
| 询价公告 | §5 第 39 条 | §5 第 40 条 |
| 磋商公告 | §5 第 41 条 | §5 第 42 条 |
| 谈判公告 | §5 第 43 条 | §5 第 44 条 |

C 层采购意向 5 条按品类线铺开（§5 第 45~49 条）：过敏原线 / 自免线 / 自免长尾线 / 仪器线 / 泛化兜底。

**待验证假设（多意图词堆叠）**：§4 规定"同一条 query 只用一个意图词，不堆砌"，但 8-14 实验只比过"零意图 vs 一意图"，**从未比过"一意图 vs 多意图"**。原设想是豆包作为语义检索可能把 `过敏原 sIgE 检测试剂 招标 采购 询价 采购意向` 当软 OR 处理，若成立则以 1× 成本拿到并集覆盖。

## 4. Query 构造规则（2026-08-26 重写）

**规则只有一条：每条 Query 是一个不含空格的词。**

官方文档 `Query` 字段原文：「用户搜索query，1~100个字符(过长会截断)，**不支持多词搜索**」。

**2026-08-26 实测**（TimeRange 同为 `2026-08-24..2026-08-25`）：

| Query | ResultCount |
|---|---|
| `过敏原检测 过敏检测 过敏源 变应原 变态反应 试剂 招标公告`（旧 §5 第 1 条） | **0** |
| `过敏原 招标`（仅两词） | **0** |
| `过敏原`（单词） | 1 |

拉宽到 `OneWeek` 后差异同样成立，且多词版**返回的还是更旧的一批**：`过敏原 招标` 得 5 条最新只到 08-21，`过敏原` 得 4 条到 08-24。

### 4.1 被本次重构推翻的旧规则

| 旧规则 | 状态 |
|---|---|
| 意图词必带，无例外 | **作废**——意图移到 `Sites` 白名单 |
| 结构：3~6 个品类词 + 意图词 + 年份 | **作废**——不允许任何拼接 |
| 一条 query 品类词不超过 6 个 | **作废**——上限是 1 |
| 同组拼、跨组不拼 | **作废**——无拼接可言 |
| 变体分散使用，不同站群用词习惯不同 | **作废**——站群差异由白名单覆盖 |

2026-08-18 合并实验的结论「词数与召回强负相关」方向是对的，但归因错了：当时以为是语义稀释，实际是 API 根本不做多词检索。那个实验里「6 个词比 10 个词好」只是「两个都很差，前者没那么差」。

### 4.2 仍然有效的规则

- **变体补查**：错写变体（`过敏源`）与同义变体（`变应原`）现在各自就是独立单词，按 §11 边际贡献决定是否留在清单，不再「并入主词 query」。
- **年份不加**：时效由 `TimeRange` + 本地日期过滤承担。
- **长度校验保留**：仍需 ≤100 字符。单词不可能超，作兜底。

## 11. 词表边际贡献实测方法（2026-08-26 建立）

§5 清单不靠直觉编排，靠实测。本节固化方法，便于日后复跑。

**为什么需要它**：旧清单的 49 条从未被单独评估过价值。2026-08-26 首次全量测量发现 **196 个候选词里 142 个零相关产出**——超过七成的调用在空转。

**流程**：

1. **构造候选词池**——把现清单展开去重，并入 §1~§3 各层词表，剔除 §10.1 硬排除品类。2026-08-26 首次执行得 196 词。
2. **逐词单发一次检索**——固定 `Sites` 白名单、`TimeRange=OneWeek`、`Count=50`，每词一次调用（0.01 元/次，196 词约 2 元）。
3. **按 §9 + §10.1 给每条结果打分**——2 分＝精准命中（过敏/自免/细胞因子，或方法学词搭配检验语境）；1 分＝宽线索（整批检验试剂/耗材招采，目标品类常藏在清单里）；0 分＝无关。
4. **贪心选词**——每轮选「边际新增相关公告数」最大的词，直到无新增。产出即 §5 的有序清单。
5. **按拐点截断**——取边际收益明显衰减处。2026-08-26 取 30 词（89% 覆盖），未取 40 词（100% 覆盖但成本 +33%）。

**口径必须用「独有相关产出」而非「总产出」**——总产出高但全被其他词覆盖的词是纯冗余，这正是旧清单浪费的主因。

**复跑时机**：产品线变动、`Sites` 白名单显著调整、或 §12 裁撤规则连续触发时。脚本见 `.tmp/wordtest.py`（一次性实验脚本，未纳入管线）。

## 12. 清单演进规则（query 归因与裁撤）

清单是固定的，但**不是永久的**——它按数据演进，不按直觉演进。2026-08-18 前无法评估任何一条 query 的价值：seen.json 每条记录存了 30 个字段，唯独没有"这条是哪个 query 捞到的"，于是"要不要加词、要不要扩意图"只能靠猜。本节把它变成算术题。

**归因数据（阶段 1、5 采集，见 SKILL.md）**：

- 每条候选记 `found_by_query`（命中它的 query 编号数组，如 `[3, 27]`）——同一 URL 被多条 query 命中时全部记上，这正是判断"哪条 query 可被替代"的依据
- 每日按 query 写一行统计到 `data/query_stats.json`：
  - `raw`：该 query 返回的候选数
  - `unique`：去重后**仅由该条 query 命中**的 URL 数（其余 29 条都没捞到）——**这是唯一有意义的贡献指标**，`raw` 高但 `unique` 恒为 0 的 query 是纯冗余
  - `pushed`：其中最终核实通过并推送成功的条数

**裁撤规则**：

1. 连续 **14 个运行日** `unique` 恒为 0 的 query → 裁撤，并在本文件变更说明里记一行（词表本身不删，词继续用于阶段 3 品类匹配）
2. 连续 14 日 `unique` > 0 但 `pushed` 恒为 0 的 query → 它在捞独有的东西，但捞的不是业务要的；先查 §6 排除词、§9 目标品类信号与 §10.1 硬排除是否需要补，再决定裁撤
3. **裁撤后按 §5 末尾的候补序列补位**（`烟曲霉` `链格孢` `IL-6` `细胞因子` `胃肠疾病抗体` `免疫分析仪` `酶联免疫` `试剂耗材` `检验设备` `化学发光法`），保持每日总量不变；总量变更需在变更说明里写明理由与成本影响
4. 样本不足 14 日不得裁撤——单日零贡献只能说明当天没有这类公告
5. **裁撤与补位都不改变 §5 的排序含义**——序号即边际贡献排名，补位词插到末尾，下次 §11 复跑时重排

> 2026-08-26：`query_stats.json` 里 2026-08-18~25 期间按旧 49 条多词清单积累的 `raw`/`unique` 数据**不可与新清单比较**——旧清单大部分 query 实际返回 0 条（原因见 §4），其 `unique` 分布反映的是"哪条多词 query 碰巧没被 API 判死"，不是词的真实贡献。新清单的 14 日观察窗从下一个运行日重新起算。

**观察名单（2026-08-26 重置）**：

旧名单（原 §5 第 39/41/43 条、第 31~34 条）随多词清单一并作废。新清单的 30 条均由 §11 实测选出、当日均有独有产出，暂无观察对象。首批需要留意的是 §5 末段边际仅 +1 的那批词（第 18~30 条）——它们在单日样本里只贡献 1 条，需累计 14 日才能区分「稳定低产」与「当天恰好没有」。
