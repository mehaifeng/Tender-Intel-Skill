# 公告去重与发送登记

去重对象是**一条公告**，有一个例外：**同一个招标的更正类公告**。

同一项目的采购意向、招标、不同轮次、不同批次、不同包号仍是不同公告，各自值得推送。
但公告推给销售之后他们就开始自主跟进了，之后的更正/变更/澄清不必再推一次——这条由
下面的「后续阶段压制」处理。中标、成交、废标、流标、终止、合同这些有结论的公告，在
`prepare` 的 `concluded` 闸门就已经出局，不走去重这条路。

列表仍以 `title`、`sm_names` 预筛，保留按调用计费的节省；已入账记录能够在列表阶段确认
身份时，连详情都不再获取。检索适配器、`prepare` 与发送门禁调用**同一个漏斗**，三处判重
不会走偏。

## 唯一真相源是飞书多维表格

本地**没有**去重库。台账就是飞书那张多维表格，通过开放接口读写：

- 检索开头拉一份全量快照写进运行目录 `<检索目录>/ledger_snapshot.json`，供列表预筛与
  `prepare` 复用，整轮口径一致；
- 发送前**再拉一次最新的**重新查重，这样别人手工加的行、另一台机器刚写的行都算数；
- 快照是运行产物，删掉重跑即可，不参与跨运行的记忆，也不需要备份或合并。

拉不到台账时整轮停下（检索层会写下 `ledger_fetch_failed` 摘要，`prepare` 拒绝在这个目录
上排队），**绝不按空台账继续**——那等于把历史公告重发一遍。

凭据见 `config/feishu_app.example.json`。应用需开通 `bitable:app`，并在目标多维表格里
通过「添加文档应用」加为协作者；只申请权限不加协作者会被拒。

## 分层漏斗：让确定性规则定案，模型只接窄带

查重最怕把整批候选丢给模型逐条比对——慢、贵、还不稳定。`scripts/dedup_match.py` 分四层
依次收口，**前一层定了案就不进下一层**：

| 层 | 依据 | 是否用模型 |
|---|---|---|
| L1 强身份 | 来源公告 ID、原始及备用链接、采购人+标题+日期、项目编号 | 否 |
| L1 后续阶段 | 同一招标已入账时，它的更正/变更/澄清不再推 | 否 |
| L2 字符级 | 裁剪归一后的标题做 3-gram Jaccard 与序列比取大 | 否 |
| L3 正文 | 标题落中间带时再比正文摘要 | 否 |
| L4 语义 | 前三层都没定下来的少数配对 | 是 |

进入 L2 之前先过**硬门**：公告阶段、项目编号、采购人、轮次/批次/包号任一明确冲突，或
日期差超过 3 天，直接判为不同公告，连相似度都不算。硬门与 `tender_identity.duplicate_reason`
用同一套前置条件，两处判重不会走偏。

阈值在 `dedup_match.py` 顶部：标题 ≥0.90 判重、<0.55 判新；中间带再看正文，正文 ≥0.80
判重、≤0.25 判新；仍未定案才生成语义配对。标题字符级再像，只要既没有采购人佐证、双方
标题也不是点名医院的长标题，就不敢直接判重，一律交给 L4。

每条候选最多带 3 个台账行去问模型（`TOP_K`）；一次运行的语义配对超过 60 个
（`MAX_SEMANTIC_PAIRS`）直接报错——那说明台账或检索窗口出了问题，不该靠模型硬扛。

### 身份规则细节

1. 优先匹配来源公告 ID、原始链接及备用链接。链接保留 `#/详情?公告ID=…` 路由，排序 query，
   只移除已知跟踪参数；网页首页与搜索结果页不作为公告身份。
2. 换链接的转载用采购人、标题、发布日期匹配；最多容忍 3 天日期差。更正公告不同日期不按
   转载合并。采购人只用整名/整别名唯一医院库匹配归一，不用子串相似匹配；接口给的名字常
   多带一层行政区前缀（`云南省玉溪市人民医院` ↔ 手工录入的 `玉溪市人民医院`），剥掉前缀后
   仍能整名唯一命中才归一，剥完对不上或对上多条就保持原样。标题可剥来源栏目
   标签、标点及与发布日期一致的尾部日期，可以兼容标题中的重复采购人前缀。
3. 标题改变但项目编号、公告阶段、轮次/批次/包号都一致，且日期在 30 天内，判同一公告。
   项目编号在一个项目的生命周期里不变，所以这条不要求采购人也存在——台账里 336/386 行
   压根没存项目编号，能对上的那少数几行反而是最硬的证据。项目编号明确冲突时永不合并。
4. 标题被来源明确截断时，只允许足够长的同日前缀匹配。采购人缺失时，只有包含具体医院名的
   长标题可以兼容旧台账；通用模板标题不能把未知采购人当通配符。
5. 不按裸标题、裸项目号、关键词重叠判重。采购意向汇总页不凭标题前缀吞并某个项目明细。

同 URL 被复用到不同阶段或明确不同轮次时仍保留。

### 后续阶段压制（`_followup_match`）

一条招标推给销售之后他们已经在跟进，同一个招标之后的**更正、变更、澄清、补充、答疑**
不再推第二次。判定条件全部满足才压制：

- 候选的阶段是更正类（`stage()` 把澄清/补充/答疑也归到「更正」）；
- 轮次、批次、包号与台账行**完全一致**——所以二次招标、重新招标、同一项目的另一个包
  都不受影响，它们对销售是新的投标机会；
- 日期相差不超过 90 天（`FOLLOWUP_DAYS`）；
- 锚点二选一：项目编号一致，或者**同一采购人 + 剥掉体裁词后的标的主体相似度 ≥0.75**
  （`tender_core()` 把「关于…的更正公告」「…公开招标公告」这类体裁词从首尾剥掉，
  更正公告与原公告的差别几乎全在这些词上，剥完通常完全相同）。

**台账里没有这个招标时，更正公告照推**——那种情况下它本身就是我们第一次捞到这个标。
2026-09-07 的台账里 12 条更正公告只有 2 条能找到对应原招标，剩下 10 条都属于这一类，
所以不能见更正就丢。

代价要认：截止时间提前、技术参数修改这类变动，销售不会再收到推送，得靠自己盯已跟进
的标。这是业务方 2026-09-07 明确选定的口径。

## 语义判定出口

L4 的候选写进 `pipeline/semantic_review.jsonl`，计入 manifest 的 `counts.semantic_review`。
它们**不进队列、不生成载荷**；即使手工塞进队列，发送门禁也会拦下。

每行只给模型判定必需的最小信息：双方的标题、采购人、发布时间、项目编号、200 字正文摘要，
以及两个相似度。判定时**只读这个文件**，不必回头翻正文或台账快照。

```bash
python scripts/tender_pipeline.py resolve-semantic --run-dir <检索目录> --decisions <判定文件>
```

判定文件是一个 JSON 数组，每项 `{"pair_id": …, "same": true|false, "note": "依据"}`。
`note` 不得为空；`pair_id` 必须来自本次待判清单。口径是**同一采购人的同一次采购行为**才算
同一条公告；不同轮次、包号、阶段、标的一律 `false`，证据不足也 `false` 并写明不足之处——
放行后面还有核实与推送两道关，误判重复会让一条真公告永远发不出去。

结论存在 `pipeline/semantic_decisions.json`，属于本次运行。队列在 `prepare` 时已定稿，
登记后要重跑 `prepare --search-dir <检索目录> --mode <原模式> --force` 才会生效；
`<原模式>` 照抄 manifest 的 `daily-push` 或 `report-only`——省略 `--mode` 会落回默认的
`daily-push`，把离线运行升级成生产写入。`--force` 不会丢结论。

**跨运行不保留**：下一轮检索若又捞到同一条公告且它仍未入账，会再次进入语义判定。这是移除
本地状态换来的代价，可接受是因为判定为「不是重复」的公告当轮就会被推送，此后台账里有它，
再遇到就是 L1 强命中。

## 推送与未知结果

`send_record.py` 在同一把快照锁内执行：

1. 重新拉取飞书台账，用同一套漏斗再查一次重。已入账则返回 `sent: false, already_seen: true`，
   零写入。
2. 落在语义窄带的直接拒发，要求先 `resolve-semantic`。
3. 16 字段载荷映射成表字段后写入。`科室`→`科室名称`、`命中关键词`→`关键词命中`、
   `内容（检索的摘要）`→`内容`；值为 `null` 的字段**不传**，单元格保持真正的空。
   `标讯来源=AI收集` 与 `标讯状态=新插入` 由发送器补齐，否则新行缺来源与初始状态；
   `是否已推送` 和两个时间戳留给表格自己的工作流填。
   单选字段的值不在选项列表里会被丢掉，发送器不静默丢，写进回执的 `dropped_fields`。
4. 只有接口返回 `record_id` 才算成功；成功后写回执并把新行并进本次快照，供同批后续候选查重。

写入结果未知（超时、连接中断）时**按链接回查**：

- 回查到那一行 → 写入其实成功了，按成功登记，不重复写；
- 回查不到 → 停下并报错，**不重试**。下一轮拉取台账会自然消解，手工重发才会造成重复行。

多维表格没有唯一约束、没有条件写，所以「拉取 → 比对 → 写入」之间仍有秒级窗口。部署为
单一生产写入端；多机同时写入不受这把本地锁保护。

## 台账里认不出的行

`链接` 是台账里唯一 100% 覆盖的身份字段，所以它是 L1 的主力。别人手工加的行
（`标讯来源` 为「员工录入」）往往没有项目编号，采购人也可能空着——这类行只能靠 L2/L3/L4
认，语义配对多一些是正常的，比原先完全看不见它们要好。
