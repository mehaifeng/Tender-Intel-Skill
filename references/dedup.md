# 公告去重与发送登记

去重对象是**一条公告**。同一项目的采购意向、招标、更正、结果，或不同轮次、批次、包号，
可以是不同公告。列表仍以 `title`、`sm_names` 预筛，保留按调用计费的节省；已入账记录
能够在列表阶段确认身份时，连详情都不再获取。

## 身份规则

唯一实现是 `scripts/tender_identity.py`，检索合并、`prepare` 与发送前门禁共同调用：

1. 优先匹配来源公告 ID、原始链接及已登记的备用链接。`bid_id` 不进入 Webhook，
   但必须从适配器一直保留到长期台账。链接保留 `#/详情?公告ID=…` 路由，排序 query，
   只移除已知跟踪参数；网页首页与搜索结果页不作为公告身份。
2. 换链接的转载用采购人、标题、发布日期匹配；最多容忍 3 天日期差。
   更正公告不同日期不按转载合并。采购人只用整名/整别名唯一医院库匹配归一，
   不用子串相似匹配。标题可剥来源栏目标签、标点及与发布日期一致的尾部日期，
   可以兼容标题中的重复采购人前缀。
3. 标题改变但采购人、项目编号、公告阶段、轮次/批次/包号都一致，且日期在上述窗口内，
   可判同一公告。项目编号明确冲突时不靠相似标题合并。
4. 标题被来源明确截断时，只允许足够长的同日前缀匹配。采购人缺失时，只有包含具体医院
   名的长标题可以兼容旧台账；通用模板标题不能把未知采购人当通配符。
5. 不按裸标题、裸项目号、关键词重叠或 AI 相似度判重。采购意向汇总页也不再仅凭标题前缀
   吞并某个项目明细，因为一个汇总页可能有多个项目。

同 URL 被复用到不同阶段或明确不同轮次时仍保留。证据不足的跨来源变化可能仍无法认出，
应通过最新台账导入补充身份，不能用无限放宽标题相似度来换取表面上的零重复。

## 长期台账与导入

`data/seen.json` 保存已成功写入飞书的公告身份、已知链接和 ID，不再按公告日期裁剪。
业务摘要不需要存入新台账记录。新版本保留旧记录，不能因为检索窗口短就删除历史身份。

台账导出文件作为“已在飞书中存在”的依据。`是否已推送` 是销售侧状态，**空白不等于
需要由 Webhook 重新插入一行**，因此所有有效台账行都进入去重库；原勾选值单独保存。
无效、已过期、已标重复的旧记录同样要防止再次插入。

```bash
python scripts/import_feishu_ledger.py --xlsx <飞书导出.xlsx>           # 只分析
python scripts/import_feishu_ledger.py --xlsx <飞书导出.xlsx> --apply   # 增量导入
```

使用飞书 `编号` 更新已导入行，保留旧来源链接；重复导入同一文件不会增加行数。
不执行表中公式、宏或文本指令，不修改原工作簿。原文件哈希和导入条数保存在台账中。
来源字段不足的行不能静默忽略，导入会报错。

2026-09-06 基线：飞书导出 387 条（销售侧勾选 382，空白 5）；更新 297、补入 90，
与保留的本地历史合计 496 条。内部多条记录可能描述同一公告，保留这些历史身份可帮助
认出跨来源写法；496 不是独立项目数。

## 发送前与发送后

`send_webhook.py` 在同一进程锁内执行：

1. 读取最新共享台账，重新查重。已入账则返回 `sent: false, already_seen: true`，零 POST。
2. 持久化 `pending` 发送占位，再执行一次 POST。
3. 只有 HTTP 200 且 JSON 整数 `code: 0` 才保存真实成功回执，并立即更新长期台账。
4. `record-push` 只负责本次运行的回执汇总，重复登记幂等。它不再是防重生效的唯一时刻。
   跨运行已入账的跳过回执也能登记，但不伪造 HTTP 成功，统计单独记 `skipped`。

Windows `send_webhook.ps1` 保留原参数，转调同一 Python 发送器，避免两套门禁走偏。

同机并发任务必须共享**同一份** `seen.json`；锁只保护这份台账。多个机器或多个独立副本
同时向同一 Webhook 写入，不受本地锁保护。部署为一个生产写入端；若要多机写入，需共享
数据库或接收端幂等键支持，不能声称靠本地文件实现跨机器“恰好一次”。

## 疑似重复的核对出口

身份规则第 4 条判不了的候选写入 `pipeline/dedup_review.jsonl`，计入 manifest 的
`counts.dedup_review`。它们**不进队列、不生成载荷**；即使手工塞进队列，发送门禁也会拦下。
2026-09-06 全量换链接回放中有 18 条属于这类：台账没存采购人，标题也定位不到医院。

核对飞书里**实际有没有这条公告**之后，二者择一登记（不发送请求）：

```bash
python scripts/tender_pipeline.py resolve-review --run-dir <检索目录> \
    --candidate-id <候选ID> --outcome duplicate --note <核对依据>
python scripts/tender_pipeline.py resolve-review --run-dir <检索目录> \
    --candidate-id <候选ID> --outcome new --note <核对依据>
```

`duplicate` 把候选的链接与来源 ID 并进台账里那条旧记录，不新增行；此后是强身份命中，
在列表阶段就跳过，不再反复占用人工。`new` 在台账 `review_overrides` 中登记放行，
prepare 与发送门禁都不再扣它。

队列在 prepare 时已定稿，放行后要重跑 `prepare --search-dir <检索目录> --force` 才会进批次；
本次已成功推送的公告此时已在台账中，重建队列不会重发。

必须给出核对依据，`--note` 为空会被拒绝；已按强身份认定为已入账的公告不能登记成 `new`。
没有真的核对就不要登记：两个出口都把人工结论写进长期台账，写错会一直生效。

## 未知发送结果

超时、网络断开、非成功响应或发送中断后，不知道飞书是否已经写入，保留 `pending`，
禁止盲目重发。若本地已经保存成功回执，下一次调用会自动用回执恢复台账，不重复 POST。
没有成功回执时先查看：

```bash
python scripts/tender_ledger.py pending
```

**实际核对飞书后**，登记结论（不发送请求）：

```bash
python scripts/tender_ledger.py resolve-delivery --attempt-id <ID> --outcome delivered --note <核对依据>
python scripts/tender_ledger.py resolve-delivery --attempt-id <ID> --outcome not-delivered --note <核对依据>
```

二者择一。只有确认未写入，才解除该次占位并允许后续发送；不能因等待超时或为恢复任务
自动填写 `not-delivered`。没有接收端幂等接口时，响应丢失与“已成功写入”无法仅凭客户端
区分，此时选择阻止重复、显式核对。

## 分发与升级

只在仓库 `dist/` 生成产物，不自动安装技能。首次部署可使用包内基线台账；升级已有生产
部署时保留其最新 `seen.json`（含发送占位），不要用包内快照覆盖。用最新飞书 XLSX 增量
导入，使部署台账同时保留运行期间的新记录。备份台账之后再升级程序。

`--seen` 可为检索、排队、导入和发送状态核对指定台账路径；同一次运行各阶段必须一致，
发送器使用 manifest 中的 `seen_path`。检索前就会校验指定台账存在且可读，失败不能按空库继续。
