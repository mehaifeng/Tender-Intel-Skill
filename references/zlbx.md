# 知了标讯适配器

本技能的唯一信源。商业聚合库，按调用次数计费。
适配器脚本 `scripts/zlbx_search.py`，统一入口 `scripts/tender_search.py`。

## 凭证

单个 API Key，放 Header 的 `X-API-Key`。读取顺序：

1. 环境变量 `ZLBX_API_KEY`；
2. `config/zlbx.json` 的 `{"api_key": "..."}`。

两者都没有则报错退出（退出码 3）。**命令行不接受明文 Key**——避免进入进程列表和
shell 历史。`config/zlbx.json` 与 `config/feishu_app.json` 同等对待：在 `.gitignore` 中，
在 POSIX 系统上应设为权限 `0600`；禁止提交、外发，也不得进候选目录、摘要、日志或
推送载荷。模板见 `config/zlbx.example.json`。

Key 没有到期机制，不需要定期换发——这是相对旧信源最大的运维差别（旧的睿销登录态
20 天固定窗口到期、需微信重新扫码，按日常定时任务计每年约 18 次）。

## 接口

Base URL `https://mcp-server.zhiliaobiaoxun.com/api_v2`，全部 POST JSON。
本技能只用两个：

| 路径 | 用途 | 单次积分 |
|---|---|---|
| `/search_bids` | 列表检索 | 1 |
| `/get_bid_detail` | 正文、原始站点链接、附件 | 1 |

响应外层为 `{success, data, error, meta}`，实际消耗以 `meta.cost_units` 为准。

## 2026-09-05 起持续实测的行为（接口文档未写或与文档不符）

这一节是靠实跑得到的，改适配器前先读完。

1. **`keywords` 是 OR，不是 AND。** `过敏`=8、`自身抗体`=5、两者同传=13。
2. **多词 OR 会静默丢结果。** 85 词一次传时，正文含 `自身抗体` 的长沙市医健完整记录
   （bid_id 602827051）不在结果里；同参数只传 `自身抗体` 一个词就能返回。
   **根因不是词数上限，是分页不稳定**——见下一节。
3. **默认匹配模式不是全文。** 默认 / `all` / `sm` 三者等价（`过敏`=8），
   `fulltext`=116。**必须显式传 `match_modes:['fulltext']`**，否则召回掉一个数量级。
4. **`fulltext` 是分词匹配，不是精确子串。** 短片段命中数常更大，但结果集并不保证包含
   完整写法；例如 `印迹` 会漏掉一部分 `免疫印迹` 文档，`变应` 甚至可能少于 `变应原`。
   Query 清单因此同时保留有边际召回的短片段和完整写法，详见 keywords.md 的集合对照。
5. **`page_size` 上限 50**，传 100 返回 `INVALID_PARAMETER`。
6. **0 命中不计费**属实。91 条清单在 72h 窗口里约 21 条常年 0 命中，这部分免费。
7. **`pub_time` 可能比公告实际发布日早一天。** 中科大附一那条血管炎标，台账记 09-02，
   知了记 09-01。**检索窗口必须比目标窗口多放一天**，否则边界上的公告会漏。
   已由 `zlbx_search.request_window()` 落实：`--time-range 09-03..09-05` 实际请求
   `09-02..09-05`，两个窗口都写进 `search_summary.json`（`time_range` 与
   `request_time_range`）。多出来那天**不做回筛**——正因为 `pub_time` 不可靠，落在
   这天的公告可能恰恰属于目标窗口；重复的部分由长期台账在列表阶段挡掉，不额外取详情。
8. **`caller` 匹配模式不可靠**：`河北省儿童医院` 用 caller 模式搜不到自己那条过敏原
   公告，fulltext 能。凡是要确认「库里到底有没有」，只用 fulltext。
9. **`get_account_balance` 返回 404**，接口未上线，无法程序化查余额。
10. **结构化字段偶发混入 HTML 片段**（实测 `bid_no` 出现过 `</span>2641STC60596`）。
    适配器的 `_clean()` 统一剥标签。
11. **`caller_name` 与 `province`/`city` 可能分属不同主体。** 库里会收公众号推文这类
    「一篇覆盖多家医院」的内容，此时 `caller_name` 取到其中一家医院，而
    `province`/`city` 描述的是发文方——实测出现过单位=`浙江省宁波市宁海县城关医院`、
    地区=`广东省深圳市南山区`。`tender_pipeline.canonicalize_create()` 因此在采购人
    名字里的省份与接口省份矛盾时**不绑定地理字段**，退回医院索引补。
12. **同一条公告存两份记录**：一份只有标题的壳（正文写「完整信息请查看原文」），
    一份带完整正文。长沙市医健那条壳 165 字、完整记录 65,351 字，而目标品类信号
    「自身抗体」只在完整记录里。壳的标题干净，完整记录的标题**把采购人名重复了一遍**。
    去重交给 `search_common.merge_source_dirs()`，它按正文长度选代表，完整记录会赢。
13. **fulltext 覆盖平台已解析的附件，我们看不到那部分。** 知了入库时解析了标题、正文
    和附件，`match_modes:['fulltext']` 是在这三者上匹配的。因此存在这种情况：标题、
    标的物清单、返回的正文里都找不到检索词，公告却被召回——命中发生在附件里，
    照着 `source_url` 打开原页面同样看不到。实测样本：山西省心血管病医院医用耗材采购，
    `PLA2R` 捞回来的，可见文本里只有清单中的「抗磷脂酶A2受体抗体IgG测定试剂」。

    两个后果：**其一**，「按检索词回原文找一遍」会得到空结果，这不是异常。`命中关键词`
    因此改以品类信号命中的原文片段为准（见 `schema.md`），不再依赖检索词能被回找到。
    **其二**，正文只是个壳时不能判定「这条没有目标品类」——`content_access:
    public_partial` 就是提示这一点，此时宁可 `manual` 也不要 `exclude`。

## 分页不稳定，以及由此决定的分批策略

同一组词（清单前 17 条）、同一参数，连打 3 次：

- `total` 三次都稳定 = 324；
- 但每次取回的 324 条里**去重后只有 317 / 312 / 313 条**；
- 三次两两相差 3~9 条，三次并集 324、交集 300；
- 单次运行内重复出现的 7 个文档**全部落在相邻页**（1&2、3&4、5&6）。

结论：排序没有稳定的 tiebreaker，翻页时记录跨页漂移，一部分返回两次、等量的另一部分
一次都不返回。`query_bids_advanced` 的 `sort_field:'pub_time'` 修不掉（仍有 6~7 条跨页
重复），而且 2 积分/次，贵一倍，不用。

**所以代价不在「词多」，在「翻页」。** 目标是让每批的命中数落在单页以内。

分批策略实测对照（85 词 / 5 天窗口，2026-09-05，只跑列表层）：

| 配置 | 调用 | 覆盖逐词基线 | 32 条台账召回 | 其中「有效」13 条 |
|---|---|---|---|---|
| 逐词 85 次 | 92 | 100% | 27/32 | 13/13 |
| 每批 5 词 | 29 | 99.1% | 27/32 | 13/13 |
| 每批 43 词 | 16 | 97.4% | 27/32 | 13/13 |
| 85 词一次 | 14 | — | 26/32 | 12/13 |
| 按命中数装箱 | 27 | 99.7% | 27/32 | 13/13 |

装箱最优，但它需要**预先知道每个词的命中数**。适配器因此分两条路：

- **`plan_batches()` 按已知命中数装箱**（宽词单独成组，其余首次适应递减）。
  命中数存在 `data/query_hits.json`，由适配器自己维护——每次跑到单词查询就把
  `total / 窗口天数` 记下来，增量合并。
- **没有历史数据的词按 `batch_size` 平铺**，装错了由 `collect_listings()` 的
  **切半重跑**兜底（首页结果照收，不浪费那次调用），递归到每批落在单页以内。
  单个词自己就超一页时无法再切，只能翻页并接受漂移。

**别给未知词硬估权重。** 试过按 `cap/batch_size` 估，5 天窗口下每个词的估值直接
顶满一页，装箱退化成 85 组、92 次调用，比朴素平铺还差。估大估小都会走极端，
不如让它们跑一轮拿真实数。

冷热两条路的实测（同窗口、同参数）：

| | 调用 | 分组 | 切半 | 取回 |
|---|---|---|---|---|
| 首次运行（无 `query_hits.json`） | 50 | 11 | 16 | 702 |
| 第二次起（85 个词全有数据） | **27** | 20 | 0 | 700 |

装箱配置连跑两次，台账召回都是 27/32、有效 13/13，文档级漂移约 3 条（0.4%），
不触及台账召回。试过「对需要翻页的组重跑一次取并集」补漂移：调用 27→39，取回不变，
**白花 12 积分，不做**。

## 成本

一次运行 = **列表调用 + 每条通过预筛的候选一次详情调用**。

2026-09-05 全流程实跑（`--time-range 2026-09-03..2026-09-05`，清单当时是 85 条）：

```
列表 38 次（当时还没有 query_hits.json；有数据后同口径降到约 27）
详情 39 次（= 通过预筛的候选数）
全库命中 363 条 → 预筛丢弃 324 条 → 候选 39 条 → 去重后 37 条
```

按热态（有 `query_hits.json`）72h 窗、每天跑一次估：列表约 27 + 详情约 39
≈ 66 积分/天 ≈ 2000 积分/月 ≈ **¥132/月**（¥500/7500 档折 ¥0.0667/积分）。

**分批省调用，但也吃掉了免费额度**：逐词跑时 85 条里约 21 条 0 命中不计费，
打包之后一批里只要有一条命中，整批就计费（实跑 `empty_batches` 为 0）。
即便如此，27 次列表调用仍远低于逐词的 77 次。

**详情调用优化（2026-09-06）**：适配器在原有标题/标的物预筛之后，用飞书台账检查列表身份，
已入账记录不再取详情，计入 `already_seen_before_detail_count`。保留72小时窗口以覆盖延迟收录，
未确认身份的候选继续正常取详情。详情缓存暂未实现，未推送的候选可能在后续窗口重复取详情。
上述历史成本不代表实时费用，应以当次 `cost_units` 为准。

**正文复核带来的成本上升（2026-09-08）**：见下面「正文里才有的信号」。同日三次实跑，
窗口都是 72h：

| | 列表 | 详情 | 合计 | 月费 | 候选 |
|---|---|---|---|---|---|
| 改动前 | 24 | 33 | 57 | ¥114 | 33 |
| 只开检验类仪器/试剂的门 | 24 | 68 | 92 | ¥184 | 41 |
| **再放宽到医疗机构的耗材器械 + 清单补 6 条完整写法** | **25** | **88** | **113** | **¥226** | **49** |

多花的钱换来两条 2026-09-07 实际漏掉的公告都被捞回，以及候选 +48%。噪声也一起进来了：
最后一次实跑复核留下 11 条，其中约 4 条（公安局 DNA 试剂、中学理化生实验室之类）明显
不是本司标的，由核实阶段判 `exclude`——弱候选不由预筛替模型做决定。

## 正文里才有的信号

**问题**：目标品类词全是试剂与抗体谱系名（`TARGET_CATEGORY_PATTERNS` 18 组），
仪器名本身不带信号。而列表层预筛只看得到**标题与标的物清单**——正文要花 1 积分取详情
才有。于是「标的物是一堆仪器、品类信号只写在正文里」的公告，在花钱看正文之前就被整条
丢掉。这等于把 `fulltext` 扩大召回的收益（实测 `过敏` 8 vs 116）又亲手扔了回去。

2026-09-07 实测漏掉的例子：

```
一批医疗设备采购项目意向公开公示(2026-JQ08-W9075)   plap.mil.cn
sm_names: 多参数生物反馈仪、全自动化学发光分析仪、凝血分析仪…共13项  → 无目标信号
正文:     变态反应科过敏原检测…                                → 命中 `变态反应`
```

**处置**：预筛判定为「无信号」时，再看一眼标的物与标题里有没有**检验类仪器或试剂**
（`search_common.LAB_ITEM_TERMS`）。有就取详情，用正文重新预筛，且**只有核心词才放行**
——宽片段（印迹 / 风湿 / 细胞因子 / 25羟基维生素D）在几十行的科室设备清单里几乎必然
出现一次，靠它放行等于全量取详情。

**这条路径不设条数上限**。撞上限就停会让「标的物是配我们试剂的仪器」这类整批漏掉，
而那正是要修的问题。超过 `REOPEN_VOLUME_WARNING`（150）只报警不截断：量真起来说明门
开得不对，该改门而不是靠截断掩盖。

**门为什么只认检验类仪器**：2026-09-08 用真实 72h 窗口（439 条列表）离线比过两种写法。

| 门 | 打开条数 | 详情合计 | 军队那条 |
|---|---|---|---|
| 任何「仪 / 仪器」+ 试剂 | 56 | 90 | 保住 |
| **只认检验类仪器 + 试剂** | **34** | **68** | **保住** |

放宽到任何「仪」会把幼儿园教学仪器、智慧药房的分光光度计、铁路保健站药品一起卷进来。
再叠加现成的非医疗机构闸门只少 1 条，不值得在列表层多加一道，那两条在 `prepare` 会挡。

同日实跑：34 条打开正文，**留下 8 条**（军队意向、柳铁中心医院试剂耗材、番禺妇幼耗材调研、
长春吉润血液科试剂、洛阳市中医院设备调研等），26 条丢弃（21 条正文也无信号，5 条只命中
宽片段）。留下的 8 条全部进入队列；其中丹东市公安局 DNA 试剂、长沙某中学理化生实验室
两条属于噪声，交给核实阶段判 `exclude`。

摘要里对应 `reopened_count` / `reopened_kept_count` / `reopened_dropped`。

`--max-details` 是常规已命中候选的详情上限；正数上限不截断“正文里才有信号”的复核分支，
否则会直接丢召回。`--max-details 0` 是特殊诊断模式，会跳过包括复核分支在内的全部详情，
只用标题与标的物清单——**不推荐**：正文是`科室`、混合包判断和 `source_url` 的唯一来源。

### 附件解析文本 `source_ext`（2026-09-09）

`get_bid_detail` 除了 `source`（正文）还回一个 **`source_ext`：知了入库时把附件
（xls / doc）解析成的 `<td>` 表格 HTML**，随同一次详情调用返回，**不另计费**。
「详见附件」那类公告的标的清单只在这里。

2026-09-09 复盘 9.7-9.8 总部补录的漏标时发现，这个字段此前**一行都没读过**——
预筛只看 `detail["source"]`。两条实例：

| 公告 | 正文 | `source_ext` 里逐字写着 |
|---|---|---|
| 茂名市电白区人民医院新增医用耗材采购需求信息公告 | 只有报名须知，清单是一份 `.xls` | `4 过敏原特异性IgE抗体检测试剂盒` |
| 关于桂林市中医医院病房能力提升项目市场调研服务采购公告 | `50项，详见附件1` | `38 全自动化学发光免疫分析仪（过敏原检测）` |

现在 `source_ext` 与正文同属正文域：二次机会那道门用它重新预筛，候选带一个
`attachment_text` 字段落盘，`prepare` 的统一层预筛、`命中关键词` 与 `科室`
都看得到它。**不并进 `content`**——`body_completeness` 与 `_extract_deadline`
判的是「公告正文本身取到没有」，灌进附件会让壳正文伪装成完整正文。

信号只在附件里时，`search_evidence.signal_only_in_attachment` 为 true，
计入 `counts.queued_signal_only_in_attachment`：核实阶段照正文回找必然是空结果，
不先说明它就会照着正文判 `exclude`。

同时 `html_to_text()` 把 `</td>` / `</th>` 也当换行。此前单元格塌成空格，
`<td>4</td><td>过敏原特异性IgE抗体检测试剂盒</td><td>用于定性检测…</td>` 会连成
一条 40 多字的长句，超过 `matched_query_keywords` 的段落上限，`命中关键词`
就只剩「过敏」这种碎片——而业务方要的正是单元格里那个完整品名。

### 二次机会再放宽两条分支（2026-09-09）

上一节留了个尾巴：桂林那条在**列表层**就被丢了（`sm_names` 只有「病房能力提升项目
市场调研服务」，既不是检验类仪器也不是耗材器械），根本没走到详情调用，
`source_ext` 再有用也读不到。`reopen_reason` 因此加了两条分支，都只在
**采购人像医疗机构**时生效：

3. **成批买设备/仪器**（`DEVICE_TERMS`）——「医疗设备一批」的清单同样只写项目名；
4. **前期公告**（`EARLY_STAGE_TERMS`：市场调研 / 调研 / 论证 / 需求公示 / 意向 /
   遴选 / 询价 / 比选 / 磋商）——`sm_names` 就是项目名本身，连「设备」都没有。

两条新分支都先过 `OFF_DOMAIN_TERMS`：医院也买交换机、复印纸、物业和等级保护测评，
那些域里不可能出现检验试剂或分析仪，开了纯属白花积分。**别域过滤只作用于新分支**
——原有的检验类仪器/试剂与耗材器械两道门已经点名了标的，
「检验科信息系统及配套试剂」不能因为 `信息系统` 被关在门外。

2026-09-09 用真实窗口（`2026-09-06..09-09`，请求窗 09-05..09-09，470 条列表）实测：

| | 列表调用 | 列表层就有信号 | 二次机会打开 | 详情合计 |
|---|---|---|---|---|
| 放宽前 | 28 | 61 | 60 | 121 |
| **放宽后** | 28 | 61 | **78** | **139** |

多开的 18 条全部取详情实跑，**12 条过了核心词那关，但逐条看原文只有 1 条是真的**
（就是桂林那条，附件第 38 项 `全自动化学发光免疫分析仪（过敏原检测）`）。
另外 11 条是这样进来的：

| 误报原文 | 条数 |
|---|---|
| `过敏` 出现在临床散文里：`过敏史`、`过敏反应`、`过敏性鼻炎`、`接触皮肤无过敏`、`过敏患者标识` | 7 |
| 型号/量表撞代号：`PBC-I 08-55`、`症状自评量表（SCL‑90）` | 2 |
| 病名撞谱系名：`治疗功能性胃肠疾病` | 1 |
| 检验外送服务里的 `过敏源及其他检验项目`（买的是服务不是试剂） | 1 |

**这不是门的问题，是 `过敏` 这个两字片段本身的问题**：新分支打开的是几十页的技术
参数与招标文件，而不是试剂清单，临床散文的密度高得多。按本项目一贯的口径
（keywords.md「宁可多捞、由核实阶段的模型判掉」），这 11 条交给核实阶段判
`exclude`；`signal_tier` 与 `signal_only_in_attachment` 都会照常带给它。真要提精度，
下一步是给品类信号加**标的上下文约束**（命中片段附近要有试剂/检测/分析仪一类的词），
那是另一笔账，会拿召回换精度，需要业务方定夺。

## 字段映射

`source_fields_from()` 把列表项映射成十六字段里可结构化直取的部分，由
`tender_pipeline.SOURCE_BOUND_FIELDS` 直接绑定，模型不再重复提取：

| 十六字段 | 接口字段 | 备注 |
|---|---|---|
| 项目编号 | `bid_no` | 剥 HTML 后照抄 |
| 单位 | `caller_name` | 采购人；代理机构在 `agency_name`，不填这里 |
| 所属省/市 | `province` | 管线归一成简称 |
| 地区 | `city` + `county` | 只给市与区县，省级全称由管线补 |
| 预算 | `money` | **单位是元**，不换算 |
| 采购方式 | `bid_method` | 照抄，管线再收敛到九个固定选项（schema.md「采购方式选项」） |
| 截止时间 | `tender_time` | **只取投标/响应截止**；`signup_time` 是报名截止，写进摘要不冒充本字段 |
| 发布时间 | `pub_time` | 权威元数据，`date_authoritative: true` |
| 标题 / 链接 / 摘要 | `title` / `source_url` / `sm_names` | 由管线绑定 |

`科室` 与产品域判断仍由核实阶段的模型做，见 [verification.md](verification.md)。

## 链接

`get_bid_detail` 返回 `source_url` = **原始站点链接**（政府采购网、省级平台、
医院自建站、公众号文章都有），匿名可访问，`链接` 字段优先用它。
知了站内链接 `url` 只作兜底，且带每次调用都不同的 `sk` 会话参数——
`search_common.TRACKING_KEYS` 已收录 `sk`，不剥掉会让同一条公告跨运行变成两个身份。
两种链接都拿不到才丢弃候选并计入 `dropped_no_url`，**任何情况下不得伪造链接占位**。
