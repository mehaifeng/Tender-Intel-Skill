# 知了标讯适配器

本技能的唯一信源。商业聚合库，按调用次数计费。
适配器脚本 `scripts/zlbx_search.py`，统一入口 `scripts/tender_search.py`。

## 凭证

单个 API Key，放 Header 的 `X-API-Key`。读取顺序：

1. 环境变量 `ZLBX_API_KEY`；
2. `config/zlbx.json` 的 `{"api_key": "..."}`。

两者都没有则报错退出（退出码 3）。**命令行不接受明文 Key**——避免进入进程列表和
shell 历史。`config/zlbx.json` 与 `config/webhook.json` 同等对待：在 `.gitignore` 中，
权限 `0600`，禁止提交、外发，也不得进候选目录、日志或 Webhook 载荷。摘要里只留
前 9 位（`mask_key()`）。模板见 `config/zlbx.example.json`。

Key 没有到期机制，不需要定期换发——这是相对旧信源最大的运维差别（旧的睿销登录态
20 天固定窗口到期、需微信重新扫码，按日常定时任务计每年约 18 次）。

## 接口

Base URL `https://mcp-server.zhiliaobiaoxun.com/api_v2`，全部 POST JSON。
本技能只用两个：

| 路径 | 用途 | 单次积分 |
|---|---|---|
| `/search_bids` | 列表检索 | 1 |
| `/get_bid_detail` | 正文、原始站点链接、附件 | 1 |

响应外层为 `{success, data, error, meta}`，实际消耗以 `meta.cost_units` 为准。

## 2026-09-05 实测行为（文档未写或与文档不符）

这一节是靠实跑得到的，改适配器前先读完。

1. **`keywords` 是 OR，不是 AND。** `过敏`=8、`自身抗体`=5、两者同传=13。
2. **多词 OR 会静默丢结果。** 85 词一次传时，正文含 `自身抗体` 的长沙市医健完整记录
   （bid_id 602827051）不在结果里；同参数只传 `自身抗体` 一个词就能返回。
   **根因不是词数上限，是分页不稳定**——见下一节。
3. **默认匹配模式不是全文。** 默认 / `all` / `sm` 三者等价（`过敏`=8），
   `fulltext`=116。**必须显式传 `match_modes:['fulltext']`**，否则召回掉一个数量级。
4. **匹配是精确子串**，短片段是超集：`印迹` 9 ⊃ `免疫印迹仪` 2、`亚类` 2 ⊃ `IgG亚类` 0、
   `风湿` 12 ⊃ `类风湿关节炎` 0。因此 keywords.md 按最短片段取词的规则在这里同样成立。
5. **`page_size` 上限 50**，传 100 返回 `INVALID_PARAMETER`。
6. **0 命中不计费**属实。85 条清单在 72h 窗口里约 21 条常年 0 命中，这部分免费。
7. **`pub_time` 可能比公告实际发布日早一天。** 中科大附一那条血管炎标，台账记 09-02，
   知了记 09-01。**检索窗口必须比目标窗口多放一天**，否则边界上的公告会漏。
8. **`caller` 匹配模式不可靠**：`河北省儿童医院` 用 caller 模式搜不到自己那条过敏原
   公告，fulltext 能。凡是要确认「库里到底有没有」，只用 fulltext。
9. **`get_account_balance` 返回 404**，接口未上线，无法程序化查余额。
10. **结构化字段偶发混入 HTML 片段**（实测 `bid_no` 出现过 `</span>2641STC60596`）。
    适配器的 `_clean()` 统一剥标签。
11. **`caller_name` 与 `province`/`city` 可能分属不同主体。** 库里会收公众号推文这类
    「一篇覆盖多家医院」的内容，此时 `caller_name` 取到其中一家医院，而
    `province`/`city` 描述的是发文方——实测出现过单位=`浙江省宁波市宁海县城关医院`、
    地区=`广东省深圳市南山区`。`tender_pipeline.canonicalize_create()` 因此在采购人
    名字里的省份与接口省份矛盾时**不绑定地理字段**，退回医院索引补。
12. **同一条公告存两份记录**：一份只有标题的壳（正文写「完整信息请查看原文」），
    一份带完整正文。长沙市医健那条壳 165 字、完整记录 65,351 字，而目标品类信号
    「自身抗体」只在完整记录里。壳的标题干净，完整记录的标题**把采购人名重复了一遍**。
    去重交给 `search_common.merge_source_dirs()`，它按正文长度选代表，完整记录会赢。

## 分页不稳定，以及由此决定的分批策略

同一组词（清单前 17 条）、同一参数，连打 3 次：

- `total` 三次都稳定 = 324；
- 但每次取回的 324 条里**去重后只有 317 / 312 / 313 条**；
- 三次两两相差 3~9 条，三次并集 324、交集 300；
- 单次运行内重复出现的 7 个文档**全部落在相邻页**（1&2、3&4、5&6）。

结论：排序没有稳定的 tiebreaker，翻页时记录跨页漂移，一部分返回两次、等量的另一部分
一次都不返回。`query_bids_advanced` 的 `sort_field:'pub_time'` 修不掉（仍有 6~7 条跨页
重复），而且 2 积分/次，贵一倍，不用。

**所以代价不在「词多」，在「翻页」。** 目标是让每批的命中数落在单页以内。

分批策略实测对照（85 词 / 5 天窗口，2026-09-05，只跑列表层）：

| 配置 | 调用 | 覆盖逐词基线 | 32 条台账召回 | 其中「有效」13 条 |
|---|---|---|---|---|
| 逐词 85 次 | 92 | 100% | 27/32 | 13/13 |
| 每批 5 词 | 29 | 99.1% | 27/32 | 13/13 |
| 每批 43 词 | 16 | 97.4% | 27/32 | 13/13 |
| 85 词一次 | 14 | — | 26/32 | 12/13 |
| 按命中数装箱 | 27 | 99.7% | 27/32 | 13/13 |

装箱最优，但它需要**预先知道每个词的命中数**。适配器因此分两条路：

- **`plan_batches()` 按已知命中数装箱**（宽词单独成组，其余首次适应递减）。
  命中数存在 `data/query_hits.json`，由适配器自己维护——每次跑到单词查询就把
  `total / 窗口天数` 记下来，增量合并。
- **没有历史数据的词按 `batch_size` 平铺**，装错了由 `collect_listings()` 的
  **切半重跑**兜底（首页结果照收，不浪费那次调用），递归到每批落在单页以内。
  单个词自己就超一页时无法再切，只能翻页并接受漂移。

**别给未知词硬估权重。** 试过按 `cap/batch_size` 估，5 天窗口下每个词的估值直接
顶满一页，装箱退化成 85 组、92 次调用，比朴素平铺还差。估大估小都会走极端，
不如让它们跑一轮拿真实数。

冷热两条路的实测（同窗口、同参数）：

| | 调用 | 分组 | 切半 | 取回 |
|---|---|---|---|---|
| 首次运行（无 `query_hits.json`） | 50 | 11 | 16 | 702 |
| 第二次起（85 个词全有数据） | **27** | 20 | 0 | 700 |

装箱配置连跑两次，台账召回都是 27/32、有效 13/13，文档级漂移约 3 条（0.4%），
不触及台账召回。试过「对需要翻页的组重跑一次取并集」补漂移：调用 27→39，取回不变，
**白花 12 积分，不做**。

## 成本

一次运行 = **列表调用 + 每条通过预筛的候选一次详情调用**。

2026-09-05 全流程实跑（`--time-range 2026-09-03..2026-09-05`，85 条清单）：

```
列表 38 次（当时还没有 query_hits.json；有数据后同口径降到约 27）
详情 39 次（= 通过预筛的候选数）
全库命中 363 条 → 预筛丢弃 324 条 → 候选 39 条 → 去重后 37 条
```

按热态（有 `query_hits.json`）72h 窗、每天跑一次估：列表约 27 + 详情约 39
≈ 66 积分/天 ≈ 2000 积分/月 ≈ **¥132/月**（¥500/7500 档折 ¥0.0667/积分）。

**分批省调用，但也吃掉了免费额度**：逐词跑时 85 条里约 21 条 0 命中不计费，
打包之后一批里只要有一条命中，整批就计费（实跑 `empty_batches` 为 0）。
即便如此，27 次列表调用仍远低于逐词的 77 次。

**详情调用优化（2026-09-06）**：适配器在原有标题/标的物预筛之后，用共享台账检查列表身份，
已入账记录不再取详情，计入 `already_seen_before_detail_count`。保留72小时窗口以覆盖延迟收录，
未确认身份的候选继续正常取详情。详情缓存暂未实现，未推送的候选可能在后续窗口重复取详情。
上述历史成本不代表导入全量台账后的实时费用，应以当次 `cost_units` 为准。

`--max-details 0` 可完全跳过详情，只用标题与标的物清单——**不推荐**：正文是
`科室`、混合包判断和 `source_url` 的唯一来源。

## 字段映射

`source_fields_from()` 把列表项映射成十六字段里可结构化直取的部分，由
`tender_pipeline.SOURCE_BOUND_FIELDS` 直接绑定，模型不再重复提取：

| 十六字段 | 接口字段 | 备注 |
|---|---|---|
| 项目编号 | `bid_no` | 剥 HTML 后照抄 |
| 单位 | `caller_name` | 采购人；代理机构在 `agency_name`，不填这里 |
| 所属省/市 | `province` | 管线归一成简称 |
| 地区 | `city` + `county` | 只给市与区县，省级全称由管线补 |
| 预算 | `money` | **单位是元**，不换算 |
| 采购方式 | `bid_method` | 照抄 |
| 截止时间 | `tender_time` | **只取投标/响应截止**；`signup_time` 是报名截止，写进摘要不冒充本字段 |
| 发布时间 | `pub_time` | 权威元数据，`date_authoritative: true` |
| 标题 / 链接 / 摘要 | `title` / `source_url` / `sm_names` | 由管线绑定 |

`科室` 与产品域判断仍由核实阶段的模型做，见 [verification.md](verification.md)。

## 链接

`get_bid_detail` 返回 `source_url` = **原始站点链接**（政府采购网、省级平台、
医院自建站、公众号文章都有），匿名可访问，`链接` 字段优先用它。
知了站内链接 `url` 只作兜底，且带每次调用都不同的 `sk` 会话参数——
`search_common.TRACKING_KEYS` 已收录 `sk`，不剥掉会让同一条公告跨运行变成两个身份。
两种链接都拿不到才丢弃候选并计入 `dropped_no_url`，**任何情况下不得伪造链接占位**。
